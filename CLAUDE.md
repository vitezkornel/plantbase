## Projekt-áttekintés

A Plantbase egy CLI AI agent, amely a felhasználó természetes nyelvű kérdését SQL-re fordítja egy növény-katalógus (`products` tábla) felett, read-only lefuttatja, és magyarul válaszol — a felhasználónak nincs szüksége SQL-tudásra. A teljes funkcionális áttekintésért és a beüzemelési lépésekért lásd a `README.md`-t, az agent pontos system promptjáért pedig a `docs/system-prompt.md`-t.

## Parancsok

### Környezet felállítása (egyszeri lépés)

```bash
pnpm install
cp .env.example .env   # legalább az ANTHROPIC_API_KEY-t töltsd ki
docker compose up -d   # elindítja a Postgres-t (konténer: plantbase-postgres)

# Létrehozza a read-only plantbase_readonly Postgres role-t (idempotens):
docker exec -i plantbase-postgres psql -U plantbase -d plantbase \
  -v pw="$POSTGRES_READONLY_PASSWORD" -f /dev/stdin < packages/db/sql/create-readonly-role.sql

pnpm --filter db exec prisma migrate deploy
pnpm --filter db exec prisma db seed
```

### Build és futtatás

```bash
pnpm nx build cli                                    # lebuildeli az apps/cli/dist/main.js-t
node apps/cli/dist/main.js ask "<kérdés>"            # egyszeri lekérdezés
node apps/cli/dist/main.js ask                       # interaktív (readline; "exit"-tel lépsz ki)
node apps/cli/dist/main.js ask --show-prompt "<k>"   # a system promptot + a teljes üzenet-tömböt is kiírja
pnpm cli ingest "<kérés>"                            # build + ingest agent: feedből frissíti a products táblát (ÍR a DB-be)
pnpm cli admin "<kérés>"                             # build + admin agent: ask-toolok + ingestProduct (ÍRHAT a DB-be)
pnpm nx dev web                                      # Next.js chat felület: http://localhost:3001 (a 3000-et a customer-chat foglalja)
pnpm nx build web                                    # production build (next build --webpack)
```

Az `apps/web` a gyökér `.env`-ből kapja a titkokat (a core maga tölti be); saját `.env*` fájlja nincs, és egyik változó sem `NEXT_PUBLIC_`.

### Teszt / lint / típusellenőrzés

```bash
pnpm nx run-many -t test                                          # teljes tesztsuite, minden projekt
pnpm nx test core                                                 # egy projekt (core | db | rag | cli | web)
pnpm nx test core -- src/tools/list-categories/list-categories-tool.spec.ts  # egyetlen tesztfájl
pnpm nx run-many -t lint,typecheck                                 # az egész workspace-re
```

A `packages/core` `tools/run-sql` és `tools/list-categories` mappája, valamint a `packages/db` `readonly-role.spec.ts` fájlja **élő** integrációs teszteket is tartalmaz a `DATABASE_URL_READONLY` ellen (a `product-writer.spec.ts` pedig a read-write `DATABASE_URL` ellen, saját tesztforrással, utána takarítva) — ezek sikeréhez a compose Postgres konténernek futnia kell, migrálva és seedelve (nincsenek mockolva).

## Architektúra

Nx monorepo (pnpm workspace-ek), egymástól függetlenül buildelhető/tesztelhető projektekkel: `core`, `db`, `rag`, `cli`, `web` (és a `customer-chat` demo).

- **`packages/core`** — az agent.
  - `agents/agent-loop.ts` — vékony wrapper a Vercel AI SDK (`ai` + `@ai-sdk/anthropic`) `generateText`/`stopWhen: stepCountIs(MAX_ITERATIONS)` (6) multi-step tool-use loopja körül: a `tools` egy név szerint kulcsolt rekord (ez maga a dispatch-tábla — nincs külön központi registry). A wrapper két, az SDK által csendben kezelt esetet emel vissza dobott hibává, hogy a korábbi, kézzel írt loop viselkedését megőrizze: a max-iterációs limit csendes levágását, és azt, ha a modell egy nem regisztrált tool nevet kér (`NoSuchToolError`) — mindent mást (egy tool `{ok:false, error}` kimenetét, vagy akár egy `execute`-on belüli el nem kapott dobást is) az SDK már magától kecsesen, a modellnek visszaadható tool-resultté alakít.
  - `agents/ask-agent/ask-agent.ts` — `askAgent(question)`, a termék felé mutató belépési pont. Bekötti a system promptot és a regisztrált toolokat (`runSqlTool`, `listCategoriesTool`) a loopba, a `logging/jsonl-logger.ts`-en keresztül JSONL interakció-logot ír, és nyers adatot ad vissza (válasz, teljes üzenet-tömb, system prompt, token-használat) — framework/I/O-független, így bármelyik hívó (ma az `apps/cli`) egyszerűen csak kiírja az eredményt.
  - `agents/ask-agent/ask-agent-stream.ts` — `streamAskAgent(messages)`, az ask-agent **streamelő** belépése (az `apps/web` használja): ugyanaz a prompt, `ASK_AGENT_TOOLS` toolkészlet, lépéslimit (`stopWhen`) és JSONL-log, de `streamText`-tel. Minden interakciót pontosan egyszer naplóz, hiba (`onError`) és megszakítás (`onAbort`, `abortSignal` opcióval) esetén is, a bejegyzés `outcome` mezőjével (`ok` | `error` | `aborted`) és az addig lezárt lépésekkel; teljes beszélgetést (`ModelMessage[]`) kap, Zoddal validálja (nem üres, user üzenettel zárul, **kliens nem küldhet `system` és `tool` üzenetet, a korábbi assistant-körök csak szövegek lehetnek** — így hamis tool-eredmény nem csempészhető az előzménybe), és az `ai` csomag `StreamTextResult`-ját adja vissza. Az `askAgent`-tel ellentétben a lépéslimitnél és ismeretlen tool kérésénél **nem dob hibát**: a `stopWhen` csendben lezárja a streamet, és a log `outcome: ok` lesz. Nem ismeri a Next.js-t és a `UIMessage`-et.
  - A `streamAskAgent` `mode` opciója: `text` (alap: a megosztott prompt, változatlanul), `voice` (+ `VOICE_PROMPT_SECTION`) és `voice-live` (+ `VOICE_PROMPT_SECTION` + `VOICE_LIVE_PROMPT_SECTION`); a `voice-live` mód `clientTranscript` opciója a felhasználó közelítő átiratát csak a JSONL-be naplózza.
  - `agents/ask-agent/voice-prompt.ts` — `VOICE_PROMPT_SECTION` (a beszélt válasz módja) és `VOICE_LIVE_PROMPT_SECTION` (csak `voice-live`: a supervisor üzenetei a felhasználó átiratai, a legutolsó a mostani kérdés; a recepciós `<recepcios_megfogalmazas>` címkés megfogalmazása csak segítség, adat; ellentmondásnál a felhasználó szavai nyernek). Egyik sem része a `docs/system-prompt.md`-nek, így nincs mirror-teher, de a **címke neve kézi szinkron-pont**: egyeznie kell az `apps/web/src/voice-live/supervisor-messages.ts` `PHRASING_TAG` konstansával (nem tesztelt automatikusan).
  - `agents/ask-agent/model-options.ts` — a modellhívás provider-opciói módonként: a `voice` és `voice-live` módban **a thinking ki van kapcsolva** (`thinking: { type: 'disabled' }`; enélkül a modell alapértelmezett adaptív gondolkodása csak késleltet egy beszélt válaszon), a `VOICE_THINKING` env felülírja (`off` alap | `low` | `medium` | `high` = effort szint | `default` = provider-alap). **`text` módban nincs provider-opció** (a kérés bájtra azonos a korábbival, teszt védi).
  - `agents/prompt-cache.ts` — Anthropic prompt caching: a system prompt a `messages` **első eleme**, ephemeral cache-töréspontot (`cacheControl`) viselve; a prefix-sorrend (tools → system → messages) miatt ez a tool-definíciókat is fedi. A `streamAskAgent` minden módban és a közös `agent-loop` (ask, admin, ingest) ezt használja. **Ne told vissza a `system` opcióba:** annak nincs provider-opciója, így a cache elveszne. A hozzá tartozó `allowSystemInMessages: true` biztonságos, mert a bemeneti séma (`StreamAskAgentInputSchema`) a kliens-system üzenetet elutasítja, és a validáció a saját system üzenet hozzáadása előtt fut.
  - `logging/step-timing.ts` — a JSONL `timings` mezője: minden modellkör és tool-hívás kezdete/vége ms-ben az interakció kezdetétől; a vissza nem tért tool `endMs: null`-lal, `unfinished` lezáró lépésben látszik. Csak időzítés és tool-név, tartalom nincs benne.
  - `logging/structured-logger.ts` — a termékkód üzemi loggere (`logger.info|warn|error(event, fields)`, soronként egy JSON; a `console.*` helyett). Az `error` mezőből csak a `name`/`message`/`stack` kerül a logba; a felhasználó üzenete soha (az a JSONL interakció-logba tartozik).
  - `agents/ask-agent/ask-agent-prompt.ts` — a `docs/system-prompt.md` XML-tartalmának szó szerinti mirror-ja. A kettő szinkronban tartása kézi konvenció (lásd a fenti házirend-szabályt), nem tesztelt automatikusan.
  - `tools/tool-outcome.ts` — a megosztott `ToolOutcome` forma, amit minden tool `execute`-ja visszaad. Minden tool a Vercel AI SDK `tool()` helperével épül fel (Zod `inputSchema` be, a modell felé menő JSON Schema-t az SDK vezeti le belőle automatikusan — nincs többé kézzel duplikált nyers JSON Schema), és egy új tool regisztrálása csak egysoros bővítés az `ask-agent.ts` `tools` rekordjában, ahelyett hogy egy karbantartandó központi dispatch-táblát kellene vezetni.
  - `tools/readonly-db-client.ts` — az egyetlen, megosztott `pg` `Pool` a `DATABASE_URL_READONLY` ellen, amit minden read-only DB-hozzáférést igénylő tool újrahasznál (jelenleg a `run-sql` és a `list-categories`). **Időkorlátok:** 5 s kapcsolódás (`connectionTimeoutMillis`), 8 s `statement_timeout` (Postgres), 10 s `query_timeout` (kliens-backstop) — egy elakadt adatbázis hibát adjon, ne lógasson egy toolt (az agent-loop nem tud megszakítani egy vissza nem térő lekérdezést, a hangos supervisor 20 s-os korlátja pedig csak a handler szintjén érvényesül).
  - `tools/run-sql/` — a `runSql` tool: a modell saját maga generálta SQL, amit a `sql-guard.ts` valid (egy kulcsszó-alapú guard, ami csak egyetlen SELECT/WITH statementet enged — elutasítja a stacked statementeket és az adatmódosító CTE-bypasseket), mielőtt egyáltalán eljutna a DB-hez.
  - `tools/list-categories/` — a `listCategories` tool: egyetlen fix `SELECT DISTINCT category FROM products` lekérdezés, nincs modell-generálta SQL, így guard-ra sincs szükség.
  - Minden tool saját könyvtára tartalmazza mindazt, ami rá jellemző (séma, guard ha van, teszt); ami több toolnak is kell, az egy szinttel feljebb lakik, ahelyett hogy toolonként duplikálódna.
  - `ingest/` — a külön **ingest agent** (`ingestProduct(request)`), ugyanazon a `runAgentLoop`-on (`maxIterations: 8`), saját prompttal és két saját toollal: `scrape-products/` (feed letöltése, tömör kivonat; nem ír) és `upsert-products/` (Zod-validálás, csomag-/akcióár-védőkorlát, majd írás a `packages/db` `upsertProducts`-án át). Csak a külön `core/ingest` alúton érhető el; a sima `core` belépési pont továbbra is csak az ask-agentet exportálja (`askAgent`, `streamAskAgent`).
  - `tools/ingest-product/` — az `ingestProduct` tool: a teljes ingest agentet (`ingestProduct`) egyetlen toolba csomagolja; az `execute` lefuttatja a belső agentet (saját loop, saját modellhívás, saját log), és a válaszát `ToolOutcome`-ként adja vissza. Írásra képes, ezért csak az admin agent regisztrálja.
  - `agents/admin-agent/` — a harmadik, **admin agent** (`adminAgent(request)`): az ask-agent négy read-only toolja + az `ingestProduct` tool; a promptja az ask-agent promptja változatlanul, plusz egy `<admin>` szekció. Csak a külön `core/admin` alúton érhető el, és csak a CLI `admin` parancsa használja.
- **`packages/db`** — a **read-write** `DATABASE_URL` kapcsolat gazdája: Prisma séma, migrációk és seed (`prisma.config.ts` — a Prisma 7 config-alapú seed-hookja, nem egy `package.json`-beli `"prisma"` kulcs; a futtatáshoz cwd = `packages/db` szükséges, pl. `pnpm --filter db exec prisma ...` formában), valamint a `lib/product-writer.ts` (`upsertProducts`) — az ingest agent egyetlen írási útja a `products` táblába, `(source, source_handle)` kulccsal. Az `sql/create-readonly-role.sql` hozza létre a külön, read-only Postgres role-t, amivel a `packages/core` read-only toolja közvetlenül kapcsolódik.
- **`apps/cli`** — csak egy commander-alapú I/O-felszín: `ask` (egyszeri vagy interaktív, az `askAgent`-be kötve), `ingest "<kérés>"` (az `ingestProduct`-ba kötve) és `admin "<kérés>"` (az `adminAgent`-be kötve) — az utóbbi kettő a futás végén lezárja a read-write kapcsolatot; nincs benne üzleti logika azon túl, hogy az stdin/argv-t bekötti az agentekbe, és kiírja a nyers eredményüket.
- **`apps/web`** — Next.js 16 (App Router) chat felület, `@ai-sdk/react` `useChat`-tel (az `@ai-sdk/react` **pontosan 2.0.264**, mert ez rögzít `ai@5.0.261`-re → egyetlen `ai` példány a fában). Az `src/app/api/chat/route.ts` validálja a UI-üzeneteket (`validateUIMessages` az `ASK_AGENT_TOOLS` ellen), majd az előzményből csak a szöveges partokat adja tovább (`text-only-history.ts`: a kliens küldte tool-, reasoning- stb. partok kiesnek), és `streamAskAgent(convertToModelMessages(...)).toUIMessageStreamResponse()`; hibánál a kliens általános üzenetet kap, a részlet a strukturált szerver-logba megy (`logger`). Az `src/chat/` a UI: a tool-lépéseket (`tool-<név>` partok) összecsukható kártyaként mutatja; egy tool `ok:false` eredménye `output-available` állapotban érkezik, ezért a `tool-step-view.ts` azt is hibaként jelzi. Az asszisztens szövegét az `assistant-markdown.tsx` rendereli Markdownként (`react-markdown` + `remark-gfm`, pontos verziókon), a modell kimenetét nem megbízható bemenetként kezelve: nyers HTML nincs (`skipHtml`, `rehype-raw` soha), kép nincs (adatszivárgási csatorna), link csak `http(s)`/`mailto` engedélylistával, `target="_blank" rel="noopener noreferrer nofollow"`-val; streamelés közben a `remend` zárja le a félkész jeleket, a kész választ nem érinti. A felhasználó üzenete sima szöveg marad. A beviteli sáv (`.composer`) az ablak alján ül (a `main` `min-height: 100dvh` flex oszlop, a sáv `margin-top: auto` + `position: sticky`), azonos szélességű Küldés/Leállítás gombbal; az automatikus görgetés csak akkor követi a streamelt választ, ha az olvasó alul van (a döntések tiszta függvények a `scroll-follow.ts`-ben, a `use-follow-bottom.ts` csak az ablakhoz köti őket), felgörgetéskor „Ugrás az aljára” gomb jelenik meg, küldéskor a nézet az aljára ugrik. Mobilra a `layout.tsx` `viewport` exportja `interactiveWidget: 'resizes-content'`-et és `viewportFit: 'cover'`-t ad. **Webpackkel fut** (`next dev/build --webpack`, `resolve.extensionAlias`), mert a core `./x.js` importjait a Turbopack nem oldja fel `.ts`-re. A Next-targetek a `@nx/next/plugin`-ből inferálódnak; a port (3001) és a `typecheck` target az `apps/web/package.json` `nx` kulcsában van. **Hangos felület (`/voice`):** a `POST /api/voice` (`src/voice/voice-handler.ts`, `voice-turn.ts`) multipart hangot kap, NDJSON-eseményfolyamot ad (átirat, szöveg, mondatonkénti mp3, filler, `timing`); a `streamAskAgent` `mode: 'voice'` opcióval fut (a core `VOICE_PROMPT_SECTION` konstansa fűződik a megosztott prompthoz, a `docs/system-prompt.md`-ben csak hivatkozás van, ezért nincs mirror-teher). STT/TTS az `ai` `experimental_transcribe`/`experimental_generateSpeech` hívásain át, `@ai-sdk/openai` **pontosan 2.0.135**; a `gpt-transcribe` kérését a `transcription-fetch.ts` igazítja (keywords/languages), mert az SDK ezt nem ismeri. Hangot nem tárolunk, az átirat csak a JSONL-naplóba kerül, az üzemi logba csak esemény + ms (a hibamezők a `safe-error-fields.ts`-en át: név + státusz). `OPENAI_API_KEY` csak szerveren, a fillerek memória-cache-ben (kulcs: modell|hang|szöveg), a gomb újranyomása megszakítja a felolvasást és a requestet. **Élő felület (`/voice/live`):** hibrid realtime + supervisor (spec: `docs/superpowers/specs/2026-10-23-web-voice-realtime-design.md`). A böngésző WebRTC-n közvetlenül az OpenAI Realtime API-hoz kapcsolódik; a realtime modell csak társalog és várakoztat, a tartalmat az `askPlantbase` tool hozza a supervisortól. `POST /api/voice/session`: 60 s-os ephemeral token, **fix szerveroldali `instructions`** (kliens szöveget nem fogad: `.strict()` enum/bool séma), memóriabeli sessionId, mintelési IP-limit (5/perc), telt tárnál 429 a kiszorítás helyett. `POST /api/voice/supervisor`: szigorú Zod, session + rate-limit, 20 s időkorlát, `streamAskAgent` `mode: 'voice-live'`; a handler az ügynököt **versenyezteti az abort-jellel** (egy vissza nem térő hívás nem élheti túl az időkorlátot), és minden kilépési ág naplóz (`supervisor_done|aborted|timeout|failed`, csak esemény + ms). **A supervisor a gpt-transcribe átiratokból dolgozik** (`supervisor-messages.ts`): a felhasználó utolsó ≤ 6 közelítő átirata user-üzenetként megy, a legutolsó a fő kérdés; a realtime modell saját kérdése (amely a mérések szerint gyakran témát téveszt) csak az utolsó üzenet végén, egy `<recepcios_megfogalmazas>` címkében, **címkézett segítségként** — soha nem system/instructions, a `<` és `>` jelek semlegesítve. A kliens a beszéd vége után legfeljebb ~1,5 s-ig várja az átiratot; ha késik vagy üres, a modell kérdése megy egyedül (régi átirat nem léphet elő fő kérdéssé). A `function_call_output` `{ userQuestion, answer, escalated }`: a modell a `userQuestion` (a pontos átirat) alapján mondja ki a választ, és ha az más témájú, mint amire gondolt, a supervisornak van igaza. A kliens logikája a React-független `voice-live/live-session.ts`: csendmérés, tétlenségi bontás (5 perc), 20 perces plafon, 5 s-os progresszív frissítés, tool-dispatch közbevágás-kezeléssel, és a `response.create` állapotgép (a „foglalt” állapot küldéskor áll be, az API `conversation_already_has_active_response` elutasítása után a tool-eredmény újrasorba kerül legfeljebb 3 próbálkozással, egy 5 s-ig nem nyugtázott create feloldódik). Az eseménylog a felhasználó képernyőjén mutatja az átiratot, a kérdéseket, a választ és a részidőket; **ezek a szövegek csak a képernyőre kerülnek**, az üzemi logba soha.

**Két DB-kapcsolat, két jog** a fő biztonsági alapelv: a `DATABASE_URL` (read-write, Prisma, csak a `packages/db` használja) vs. a `DATABASE_URL_READONLY` (csak SELECT-et engedő Postgres role, nyers `pg` kliens, csak a `packages/core` read-only toolja használja — soha nem Prismán keresztül).

- **Az ask-agent read-only marad:** a toolkészletében (`runSql`, `listCategories`, `searchKnowledge`, `customerPreferences`) nincs olyan kódút, ami írni tudna az adatbázisba — ezt két, egymástól független rétegen kényszerítjük ki: az alkalmazás-szintű SQL guard (`sql-guard.ts`) és a Postgres role saját jogosultságai. Ez az agent fut a CLI `ask` parancsában, az `apps/customer-chat` szerveren és az `apps/web`-ben (streamelve); semmilyen kapcsolóval sem kapja meg az ingest képességet (az `ask-agent.spec.ts` és az `ask-agent-stream.spec.ts` regressziós tesztje ellenőrzi, hogy csak ez a négy tool van felkínálva).
- **Az ingest agent írásra jogosult, elkülönített kódúton:** csak az `upsertProducts` toolja ír, kizárólag a `packages/db` read-write Prisma kapcsolatán át (a core nem épít saját read-write kapcsolatot), és csak a `core/ingest` alúton érhető el. A `plantbase_readonly` role jogai nem változtak.
- **Az admin agent az ingest agenten át írhat:** az `ingestProduct` toolja a teljes ingest agentet futtatja, így ugyanazon az elkülönített írási úton ír. Csak a `core/admin` alúton érhető el, és csak a CLI `admin` parancsa használja — a customer-chat soha.
